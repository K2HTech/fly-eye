# Commit convention

Fly Eye uses [Conventional Commits](https://www.conventionalcommits.org/) so the
history remains readable and can support automated changelogs and releases in
the future.

## Message format

Write the first line of each commit in this form:

```text
<type>(optional-scope): <description>
```

Use one of these types:

| Type       | Purpose                                                       |
| ---------- | ------------------------------------------------------------- |
| `feat`     | Add or change user-facing functionality.                      |
| `fix`      | Correct a defect.                                             |
| `docs`     | Change documentation only.                                    |
| `style`    | Change formatting without changing behavior.                  |
| `refactor` | Restructure code without adding a feature or fixing a defect. |
| `perf`     | Improve performance.                                          |
| `test`     | Add or update tests.                                          |
| `build`    | Change the build system or dependencies.                      |
| `ci`       | Change continuous-integration configuration.                  |
| `chore`    | Perform maintenance that does not fit another type.           |
| `revert`   | Revert an earlier commit.                                     |

The optional scope identifies the affected area, such as `ui`, `review`,
`decision`, `tauri`, or `docs`. Write the description in the imperative mood,
keep it concise, and do not end it with a period.

Examples:

```text
feat(review): add synchronized clip transport
fix(ui): prevent an empty decision state
docs: document branching workflow
```

For a breaking change, place `!` before the colon and explain the change in the
commit body:

```text
feat(tauri)!: change the desktop host configuration
```

## Pull request titles

Pull requests into `develop` are squash-merged, so the pull request title
becomes the commit recorded on `develop`. Write the title in the same
Conventional Commit format:

```text
feat(decision): add the simulated evidence panel
```

CI validates both the commits in a pull request and its title. A work-in-progress
title such as `Develop` or `Fix stuff` will fail the convention check.

## Enable validation

The repository includes a shared `commit-msg` hook. Git does not enable hooks
from a cloned repository automatically, so each contributor must run this once
from the repository root:

```bash
git config core.hooksPath .githooks
```

After it is enabled, Git rejects messages whose subject does not have an
allowed type, optional valid scope and breaking marker, and a non-empty
description. Imperative mood, concision, and punctuation remain review rules
rather than automated checks. Merge commits and messages generated by
`git revert` are accepted. The hook can be bypassed locally with `--no-verify`,
so CI repeats the syntax check for pushed commits and pull request titles.
